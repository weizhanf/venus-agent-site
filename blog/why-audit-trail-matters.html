AUDIT & COMPLIANCE

当 AI 改了你的表格，你能证明它没出错吗？

Venus Labs · 2026-06-10 · 10 分钟阅读

上个月，我们的一个用户给我发来了一封邮件，标题是："审计师要看修改记录，我拿不出来。"

背景是这样的：他用一个 AI 工具清洗了一份 6000 行的应收账款台账，清洗后的结果比原来干净多了——空值填补了、格式统一了、重复行删掉了。然后他把这份数据提交给了外部审计师。

审计师问了一个很合理的问题："这份表格被修改了多少次？每次改了什么？用的是什么逻辑？"

他答不上来。

AI 工具没有给他任何修改记录。只有一个"处理完成"的提示，和一个下载链接。

这件事让我重新思考：AI 时代的数据可信度，到底由什么来保证？

一、问题的本质：不可见的修改

在传统的 Excel 工作流里，人工修改数据是显而易见的——你知道自己改了什么，因为是你亲手改的。即便粗糙，也有迹可循：Excel 的修订历史记录、版本备份、操作日志。

但 AI 工具带来了一个新问题：修改的规模和速度超出了人工记录的能力。

一个 AI agent 在 30 秒内可以修改 5000 行数据里的 847 个值、删掉 23 行重复项、统一 12 种日期格式。这些操作如果要你手工记录，至少需要半天时间。

所以大多数 AI 工具选择了最简单的方案：不记录。或者记录一个高层次的"操作描述"，而不是可验证的证据链。

⚠ 合规风险

在金融、医疗、法律等受监管行业，"这个 AI 帮我处理了"不是可接受的审计答案。你需要能够证明：改了什么、为什么改、谁批准的、是否可以撤销。

二、什么是哈希链？（不用懂技术）

让我用一个比喻来解释。

想象你在给一份重要合同做公证。公证处的做法是：

  1. 对合同原文拍照，生成一个唯一的"指纹"（哈希值）
  2. 在合同上盖章，章上印着这个指纹
  3. 如果你之后改了合同的任何一个字，重新生成指纹，和原来的章对不上
  4. 这就证明合同被篡改了

哈希链把这个逻辑延伸到每一步操作上：

  • 第 1 步操作完成后，生成操作 A 的哈希 = H(A)
  • 第 2 步操作完成后，生成 H(B) = SHA256(操作B内容 + H(A))
  • 第 3 步：H(C) = SHA256(操作C内容 + H(B))
  • ……以此类推

因为每个哈希都包含了上一步的哈希，整条链是不可分割的。你不能偷偷修改中间某一步——修改任何一步，从那步往后的所有哈希都会失效，篡改立即暴露。

这就是比特币区块链的核心原理。我们把同样的机制用在了数据清洗的每一步操作上。

三、Venus 审计日志的实际输出

      "rows_affected": 0,
      "timestamp": "2026-06-10T09:14:22.103Z",
      "block_hash": "a1b2c3d4e5f6..."
    },
    {
      "block_id": 1,
      "op_type": "FILL_MISSING",
      "target_column": "基本工资",
      "strategy": "median_by_group",
      "group_by": "部门",
      "rows_affected": 162,
      "prev_hash": "a1b2c3d4e5f6...",
      "block_hash": "9f8e7d6c5b4a..."
    },
    {
      "block_id": 2,
      "op_type": "DEDUPLICATE",
      "key_columns": ["员工ID"],
      "keep": "first",
      "rows_removed": 15,
      "prev_hash": "9f8e7d6c5b4a...",
      "block_hash": "2c3d4e5f6a7b..."
    }
  ],
  "file_hash_output": "sha256:8b9c0d1e...",  // 结果文件指纹
  "chain_valid": true
}

这份日志回答了审计师的三个核心问题：

  1. 改了什么：`FILL_MISSING` 操作填充了"基本工资"列的 162 个空值，使用部门中位数；`DEDUPLICATE` 删除了 15 行重复的员工记录。
  2. 为什么改：策略是 `median_by_group`，按部门分组求中位数——这是在执行你下达的指令，逻辑透明。
  3. 是否被篡改：`chain_valid: true` 表示链式哈希验证通过，没有任何操作被事后修改。

四、如果有人篡改了中间一步，会发生什么？

下面这张图演示了篡改检测的工作原理：

GENESIS
原始文件
block_hash:
a1b2c3d4e5f6...
→
FILL_MISSING
162 行受影响
block_hash:
9f8e7d6c5b4a...
prev: a1b2c3d4...
→
DEDUPLICATE ⚠
被篡改！
block_hash:
INVALID ✗
prev 哈希不匹配
→
后续操作
全部失效
chain_valid:
false ✗

只要有人修改了 block_id=2 的操作内容，重新计算出来的哈希就会和原来记录的不一致，链就断了。不仅这步操作暴露，后面所有操作的哈希都会失效，无法伪造一个"修复了"的假链。

五、和传统方案的对比

❌ 传统方式
  • Excel 的修订历史只记录"谁在什么时间改了哪个单元格"
  • 无法记录批量 AI 操作的业务逻辑（"为什么这样填充"）
  • 历史记录可以被关闭或清除
  • 没有输入/输出文件的完整性指纹
  • 无法验证"这个文件就是那个文件"
✓ Venus 哈希链
  • 每步操作记录完整的业务逻辑（策略、分组依据、影响行数）
  • 链式哈希，任何篡改立即暴露
  • 无法关闭，无法删除，无法伪造
  • 输入/输出文件都有 SHA-256 指纹，可交叉验证
  • JSON 格式，审计师可用任何工具独立验证

六、这在实际合规场景里怎么用？

场景 1：年度审计

外部审计师收到你提交的财务报表。他们想验证：这份数据是否在你们用 AI 处理后被额外修改过？

你只需要提供：原始文件（ SHA-256 = 3a7f9b2c…）+ audit_log.json + 结果文件（SHA-256 = 8b9c0d1e…）。

审计师运行一行命令即可验证：

$ python verify_chain.py audit_log.json
  ✓ 输入文件哈希匹配
  ✓ 操作链完整，共 3 步
  ✓ 输出文件哈希匹配
  ✓ chain_valid: true

场景 2：内控合规

合规部门要求所有对账数据的修改都必须有记录。以前这意味着人工填写变更日志，既繁琐又容易遗漏。

用 Venus 处理的每份数据自动生成 audit_log.json，提交到公司的文档系统即可。无需额外操作。

场景 3：数据争议

甲方说："你们提供的数据和我们系统里的不一样，是你们改过了吧？"

你可以拿出原始文件的 SHA-256 指纹 + 完整的操作链，证明：数据被修改了，但是按照你们双方约定的逻辑（去掉重复行、标准化格式），没有任何"额外"修改。

七、一个真实的问题：审计日志会被 AI 自己篡改吗？

这是一个很好的问题，我们自己也反复问过自己。

Venus 的架构设计里，审计日志的写入和 AI 操作是物理分离的：

  • AI agent（S4 SandboxWorker）只有执行权，没有日志写入权
  • 哈希链的写入由独立的 AuditLogger 模块负责，不经过 AI
  • 每个操作完成后，AuditLogger 接收操作结果，然后写入哈希，AI 无法干预这个时序

此外，因为哈希链的设计，即便 AI 想篡改过去某个操作的记录，它也无法在不暴露的情况下完成——因为它没有"重建一个有效链"的权限，而你（或审计师）随时可以用独立工具验证。

Venus 核心 PII 引擎 venus-pii 完全开源（MIT 协议），包括审计相关的代码。你不需要信任我们——代码在那里，自己审查。

八、结语：可审计性是 AI 时代数据的新护城河

我们建这套系统，不是因为监管强制要求（目前还没有），而是因为我们相信：

AI 工具的价值，不只是让你快，还要让你能够对结果负责。

当你把一份数据提交给领导、提交给审计师、提交给合作方，你要能说清楚：这份数据从哪来，经历了什么，是否可信。

哈希链审计日志是我们给出的答案。它不是功能的点缀，而是 Venus 架构的核心承诺。
